# 반응형 모바일 섹션 되돌림 재현과 수정

## 보고와 확인 범위

사용자는 실제 아이폰 15 프로 맥스에서 ‘어려운 자료도, 하나씩 보면 괜찮아요’·‘사건 정보는 이렇게 알려주세요’·‘장손이와 함께 하나씩 둘러볼까요’가 쓸기 후 다시 상단에 잡힌다고 보고했다. iOS 버전은 제공되지 않았다. 이전 공개 버전 `3a13428`의 자동 검사 통과를 실기기 해결로 판단하지 않는다.

사용자는 특정 기종만 추가하지 말고 모든 휴대전화에 대응하는 반응형 검사를 요청했다. 수정 코드에는 기종 조건을 넣지 않는다. 기기 프로필은 한 재현 사례로만 사용하고, 실제 내용 높이와 화면 높이의 경계를 여러 폭에서 교차하는 검사로 확대한다.

설치된 Playwright의 `iPhone 15 Pro Max` 프로필은 보이는 영역 430×739, 화면 430×932, 화면 배율 3이다. 이는 검사 프로필의 값이며 사용자 기기에서 직접 수집한 화면 수치는 아니다. 사용한 WebKit 검사 엔진의 버전은 27.2이고, 모바일 쓸기 전체를 실제 아이폰에서 실행한 검사는 아니다.

## 재현한 목적지 계산 오류

`src/ui/journey.js`의 `moveJourney()`는 읽기 끝으로 이동할 때 매 프레임 `section.offsetHeight - innerHeight`를 계산했다. 검사 환경에서 사건 안내 높이는 862였고, 보이는 높이를 739에서 932로 바꾸면 이 거리가 123에서 0으로 바뀌었다.

이 동적 재계산은 직전 수정 `ae78856`(2026-11-06 21:21:48 +0900)에서 추가됐다. ‘보이는 높이가 달라지면 현재의 읽기 끝을 따라가야 한다’는 가정으로 넣었지만, 내용이 화면보다 짧아지면 이미 선택한 목적지가 원점이 되는 경계를 놓쳤다. 이전의 844↔780 검사에는 이 경계가 없었다.

430×739에서 사건 안내 맨 위 `scrollY=2111`로 이동한 뒤 아래로 쓸고, 이동 시작 100ms 후 430×932로 바꿨다. 브라우저의 네이티브 스냅을 끈 중간 수정본에서도 완료 위치가 2111로 돌아왔다. 따라서 읽기 끝의 동적 재계산만으로도 같은 형태의 되돌림이 발생했다.

이미 선택한 읽기 거리가 진행 방향의 반대로 줄지 않도록 한 뒤 같은 검사는 2234에 도착했다. 다음 쓸기는 새 화면 높이에서 목적지를 다시 골라 둘러보기로 나간다. 섹션의 문서상 위치와 카드 위치는 계속 현재 배치를 따른다. 처음부터 내용이 한 화면에 들어오면 길이 0인 읽기 단계는 건너뛴다.

읽기 거리를 무조건 고정하면 반대로 화면이 짧아질 때 내용 끝을 덜 보여줄 수 있다. 최종 코드는 앞으로 읽을 때 필요한 거리는 늘릴 수 있지만 줄이지 않고, 뒤로 갈 때는 반대로 처리한다. 높이가 커지거나 작아져도 목적지가 진행 반대로 되돌아가지 않게 한다.

## 스크롤 제어 충돌 제거

기존 모바일 CSS는 직접 이동 중에만 루트의 스냅을 끄고, 완료 뒤 `y mandatory`를 복원했다. 직접 계산한 읽기 끝은 섹션 시작과 다르므로 두 제어 방식이 같은 목적지를 보장하는 구조가 아니었다. 준비된 모바일 둘러보기에서는 직접 제어만 위치를 결정하게 했다. 둘러보기를 닫은 첫 화면, 준비되지 않은 이미지의 대체 표시, 업무 화면의 기존 동작은 각 조건의 기존 경로를 사용한다.

[WebKit 이슈 245722](https://bugs.webkit.org/show_bug.cgi?id=245722)는 iOS에서 루트 강제 스냅과 프로그램 이동을 함께 사용할 때 이동이 취소되거나 이전 위치로 돌아간 사례를 기록한다. [Safari 27 변경 기록](https://webkit.org/blog/18325/webkit-features-for-safari-27-0/)에는 브라우저 UI가 숨겨진 뒤 강제 스냅과 프로그램 이동이 실패하던 문제의 수정이 명시돼 있다.

[추론] 사용자 기기에 이 WebKit 이슈가 적용됐는지는 iOS 버전과 기기 로그가 없어 확정할 수 없다. 이번 수정은 해당 루트 스냅 경로를 사용하지 않게 하며, 기기 업데이트를 요구하지 않는다.

기존 Touch Events 처리도 포인터 입력이 진행 중이면 바로 반환했다. 변경 전 Chrome 감사에서는 첫 `touchmove`가 취소 가능하지만 취소되지 않았고, 이후 이벤트들이 취소 불가능했다. 이제 포인터와 함께 전달되는 터치도 첫 사용 가능한 수직 `touchmove`부터 네이티브 이동을 취소한다. 다음 위치 선택의 18px 기준은 유지한다. 입력 중인 필드·대화창·장손이 조작부·다중 터치는 기존 예외를 유지한다.

모바일 폭의 휠도 같은 목적지 목록을 사용한다. 루트 스냅에 의존하던 긴 섹션의 기본 휠 처리가 작은 읽기 구간을 넘어버리지 않도록 했다. 데스크톱의 휠 경로는 유지한다.

## 검증 기준

- 읽기 전환 중 내용이 화면보다 짧아져도 시작 위치로 되돌아가지 않고, 다음 쓸기로 다음 섹션에 도착한다.
- 준비된 모바일 둘러보기의 이동 전·중·후 루트 스냅은 `none`을 유지한다. 정해진 위치로의 부드러운 전환은 직접 제어로 검사한다.
- 첫 사용 가능한 수직 터치 이동이 취소되고, 포인터와 터치가 함께 전달돼도 네이티브 이동이 끼어들지 않는다. 각 경로에 ‘18px 미만 TouchEvent가 반드시 존재한다’는 전제를 두지 않고 첫 취소 가능 이벤트를 검사한다. 기존 1배율 DevTools 경로에는 실제 관찰한 18px 미만 이벤트의 취소 검사도 유지한다.
- 화면 크기 430×739·430×932·440×956·430×1100, 배율 3에서 전체 소개 → 안내 → 제목 → 카드 7개 → 결과 → 입력과 역방향을 검사한다.
- 검사 문서의 CSS `svh`만 739px 기준으로 고정한 모델에서도 같은 경로를 검사한다. 원본 문서·이미지와 실제 배포 파일은 변환하지 않는다.
- 짧은 화면과 휠·DevTools 변환 입력, 업무 로직·입력 항목, 첫 화면 배치와 깜빡임도 회귀 검사한다.
- `test:responsive`는 Chrome·WebKit에서 폭 280·320·360·375·390·412·430·480·600·720 각각에 대해 소개와 안내의 실제 내용 높이를 구한다. 화면이 그보다 작을 때 쓸기를 시작하고, 이동 중 그보다 크게 바꾼 뒤 다음 섹션 진입과 역방향 축소도 검사한다. 첫 화면의 주요 버튼이 화면 밖으로 잘리는지도 확인한다.
- Chrome의 실제 터치 입력으로 640×360·720×360·721×360·844×390·932×430에서 세 섹션의 전진을 검사한다. 가로 화면과 모바일 레이아웃 경계 720/721 양쪽을 포함한다. WebKit의 쓸기 검사는 마우스이며, 이 결과를 실제 iOS 터치 검사라고 표현하지 않는다.

## 로컬 검사 결과

- `test:responsive`: Chrome·WebKit에서 위 10개 폭의 두 읽기 섹션에 대한 내용 높이 교차·다음 섹션 이동·역방향 축소·버튼 범위가 전부 통과했다. Chrome의 가로 화면 5개 크기에서도 세 섹션이 앞으로 진행했다.
- `test:mobile-flow`: 390×844·320×568의 네이티브 터치·DevTools 변환 터치·휠 전체 왕복 6개 조합이 통과했다. 카드 7개, 한 번의 캐릭터 이동, 최초 터치 취소와 이동 후 루트 스냅 해제도 포함한다.
- 큰 화면 4개 크기의 네이티브 터치 왕복은 기본 `svh`와 739px 고정 모델에서 통과했다. 이 실행 뒤 추가한 최종 읽기 거리의 양방향 처리에 대해서는 10개 폭의 내용 높이 교차 검사, 기본 전체 왕복 검사, 739px 고정 모델의 `--tall --resize-only`를 재검사해 통과했다. 중간 수정본의 검사와 최종 추가 검사를 구분한다.
- `test:regression`: 원본 함수 80개·연결 36개·내장 데이터 2종, 입력/편집 106개, 타임라인 6개 시나리오·판례 8개 상태·약관 3개 분류·KCD 검색 4종·분쟁조정 20개 상태·카드뉴스 7개 양식이 일치했다. PNG 저장, 편집 저장/초기화, 뒤로가기/앞으로가기, 7개 직접 진입도 통과했다.
- `test:scroll`, `test:mobile-devtools`, `test:mobile-polish`, `test:hero`, `test:companion`이 통과했다. 첫 화면 배치는 승인된 `9fad8a0`과 5개 크기에서 일치했고, 기존 깜빡임·메뉴 안내·채팅·첨부·잡기 동작도 통과했다. 업무 스크립트·데이터·페이지 템플릿·이미지는 `70ffa6b`와 파일 차이가 없다.
- 네이티브 터치로 직접 입력 버튼을 누르며 9px의 작은 흔들림을 준 추가 검사에서도 이전 HTML과 새 HTML 모두 입력 화면에 도착했다.

구현 위치는 `src/ui/journey.js`의 `moveJourney()` 읽기 거리 처리(193행), 모바일 휠 목적지 공유(334행), `touchmove` 취소 처리(423행), `src/styles/landing.css`의 모바일 제어 방식 선택(186행)이다.

## 비교 브랜치와 공개 배포

수정은 현대해상 `7ec777a`, 가이드 `6cde46f`, 오리지널 `ff46993`에 반영했다. 가이드에서는 `test:responsive`의 10개 폭·두 엔진·가로 5개 크기를 별도 실행해 통과했다. 오리지널에서는 `--tall --resize-only`와 `--touch-only`를 실행해 내용 높이 경계·역방향 축소·카드 7개 포함 390×844·320×568 전체 왕복을 통과했다. 두 마스코트 비교 브랜치의 `src`·`scripts`·패키지·README 차이는 `src/mascot-assets.json` 선택 경로뿐이다. 현대해상의 추가 테마는 유지한다.

[배포 실행 42229849247](https://github.com/wkdal1433/jangsoni/actions/runs/42229849247)이 `7ec777a842581497ab56e555722aa3ff9712c80e`을 성공적으로 배포했다. [새 확인 주소](https://wkdal1433.github.io/jangsoni/?mobile-fix=7ec777a)는 HTTP 200이며 HTML은 검증한 현대해상 HTML과 줄바꿈 통일 후 정확히 일치했다. SHA-256은 `2a5d02cb52651c98d7cd709ceced32f84b2d2552ce4ca4e4abb61efee5eb134a`이다. 기존 QR 파일도 공개 파일과 일치했다.

공개 주소의 1440×900·390×844에서 첫 깜빡임, 소개 전환, 업무 진입·복귀, 변환 터치 카드 이동, 장손이 길게 잡기와 선택 방지가 통과했다. 공개 URL의 `--tall --touch-only`에서는 430×739·430×932·440×956 왕복이 통과했고, 아래 입력 예외를 바로잡은 검사로 430×1100 전체 경로도 별도 재검사해 통과했다. 두 엔진의 높이 변경·입력/대화상자 예외 검사도 함께 통과했다.

### 입력 영역의 일반 스크롤 검사

430×1100의 첫 공개 검사에서는 입력 화면에서 결과 예시로 되돌아갈 때 `target=8115.25`, `scrollY=8113`이 관찰됐다. 입력 영역은 일반 스크롤을 유지하므로 마지막 쓸기가 설명 섹션의 위쪽 경계를 조금 넘을 수 있다. 설명 섹션 내부의 직접 제어와 동일하게 정확한 위치 도착을 요구하던 검사 전제를 수정했다. 실제 사이트 코드는 이 검사 조정으로 바꾸지 않았다.

이 예외는 입력 영역에서 설명으로 돌아오는 경로에만 적용한다. 실제 터치 위치가 결과 예시 안이고 마지막 기능 카드를 건너뛰지 않았는지 검사한 뒤, 다음 제어 입력부터 카드 7개·둘러보기 제목·사건 안내·소개까지 기존 2px 이내 도착 검사를 그대로 통과해야 한다. 중간 위치로 강제 이동하지 않는다. `--size=430x1100`은 전체 경로의 해당 크기만 골라 재검사하는 옵션이다.

실제 사용자 기기에서 세 구간의 되돌림이 해소됐다는 회신은 아직 받지 않았다. 자동 검사 범위와 실물 기기 확인을 구분한다. `main`은 기존 `549f2e1837d01f392cda7d40959d16d137667e32`을 유지한다.
