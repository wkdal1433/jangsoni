# 모바일 섹션 이동 중단 추가 검사

## 사용자 보고와 검사 한계

사용자는 실제 아이폰 Chrome에서 둘러보기를 펼친 뒤 두 구간에서 아래로 내려가지 않거나 버벅였다고 보고했다. 정확한 두 섹션 이름과 기기 버전은 제공되지 않았다. PC 모바일 미리보기의 휠 문제만 고쳐서 이 보고를 해결한 것으로 취급하지 않는다.

이 보고서의 브라우저 결과는 격리된 프로젝트 미리보기에서 얻었다. 실제 아이폰에 연결해 터치·주소창 이벤트를 수집한 결과는 아니다. WebKit에서는 모바일 배치의 마우스 드래그와 화면 크기 변경을 검사하며, 네이티브 터치 쓸기 전체 경로는 Chrome에서 검사한다.

## 확인한 코드와 실패

1. `src/ui/journey.js`의 `resize` 처리에서 높이만 달라져도 `stopJourneyTransition()`을 호출했다. 이 취소 조건은 `cda396e`(2026-11-06 11:22:12 +0900)에 나타나며, `c932e54`에서 모바일 섹션·카드 전환이 추가된 뒤에도 유지됐다. `617a19b` 배포본에서 소개 첫 쓸기 중 390×844를 390×780으로 바꾸자, 목적지 1311.625 대신 1052에서 정지했다. 새 `test:mobile-flow`를 해당 커밋 HTML에 실행하면 이 조건에서 실패한다.
2. `mobileDestination()`은 사건 정보 안내 구간에서 역방향 목적지를 항상 같은 구간의 읽기 끝으로 반환했다. `7bdd691`(2026-11-06 12:27:45 +0900)이 이 분기를 추가했다. 연속 경로 검사에서는 안내 맨 위 2091.625로 돌아가야 할 때 2102에서 제자리를 반복했다. 소개와 안내의 맨 위·읽기 끝·둘러보기 제목을 각각 후보로 두고, 실제로 현재 위치보다 앞뒤에 있는 목적지만 선택하도록 수정했다.
3. `onJourneyWheel()`은 모바일 폭을 제외했다. 모바일 배치에서 140px 휠을 반복하면 소개 읽기 끝에서 멈추는 현상을 `5e214e3`, `cda396e`, `c932e54`, `7bdd691`, `cb5d70f`, `ea623d0`, `d70437f`, `617a19b` HTML에서 재현했다. 이 관찰만으로 최초 도입 커밋을 단정하지 않는다. 휠도 모바일 카드의 실제 스냅 위치와 소개의 두 단계 목적지를 사용하게 했다.
4. `onMobilePointerDown()`의 대상은 카드판과 소개 섹션뿐이었다. 안내·둘러보기 제목·결과 예시의 느린 쓸기는 다른 경로를 탔다. Chrome의 실제 마우스→터치 변환으로 연속 역방향 검사를 하니 결과 예시 → 마지막 카드에서 목적지 6576.6875 대신 6656에 멈췄다. 전환을 담당하는 첫 화면·소개·안내·둘러보기·결과 예시의 포인터 입력과 목적지 목록을 통일했다. `touch-action`의 적용 조건도 둘러보기 열림·마스코트 준비·입력 포커스 없음·대화상자 닫힘 조건과 맞췄다. 버튼을 쓸 때는 이동하고, 단순 탭은 기존 버튼 동작을 유지한다.

최근 눈 깜빡임 수정 `fa72571` 이전 HTML에서도 위 실패 경로가 나타났다. 기존 검사는 섹션 위치를 직접 맞춰 경계를 확인하거나 안내 구간의 읽기 끝에서 시작했으므로, 연속 역방향 경로와 전환 중 높이 변경을 검증한 것이 아니었다.

## 수정 범위

- 모바일에서 폭이 유지되는 높이 변경은 진행 중인 쓸기·이동을 취소하지 않는다. 폭 변경·데스크톱 크기 변경·업무 화면 이동·입력 포커스·모션 감소 설정의 취소는 유지한다.
- 전환 목적지는 고정 숫자만 사용하지 않고 해당 섹션의 현재 시작·읽기 끝 또는 카드의 현재 스냅 위치를 따른다. 높이 변경 중에도 새 목적지에 도착한다.
- 안내 구간의 제자리 목적지 선택과 모바일 폭 휠 제외를 수정한다.
- CSS의 터치 처리 조건을 맞춘다. 업무 스크립트·입력 필드·내장 데이터·이미지·색·크기·배치는 변경하지 않는다.

## 검증

새 `scripts/verify-mobile-flow.mjs`는 다음을 별개로 검사한다.

- Chrome·WebKit: 소개 내부·다음 섹션 진입·카드 정방향·역방향 전환 중 높이를 바꾸고 새 목적지 도착 여부를 검사한다.
- Chrome·WebKit: 첫 화면의 읽기 끝·앞뒤 섹션 전환, 입력 포커스와 열린 대화상자에서 터치 제어 해제를 검사한다. `--resize-only`는 이 묶음만 재실행한다.
- Chrome 390×844·320×568: 네이티브 Touch Events, DevTools 마우스→터치 변환, 휠로 소개 → 사건 안내 → 둘러보기 제목 → 카드 7개 → 결과 예시 → 입력 화면과 역방향을 연속 통과한다. 이 경로에서는 프로그램으로 중간 섹션에 점프하지 않는다.
- `--touch-only`는 전체 경로 중 Chrome의 네이티브 터치 쓸기 두 크기를 선택한다. Chrome·WebKit의 높이 변경·첫 화면 왕복·입력/대화상자 예외 검사도 함께 실행한다. 공개 배포 주소에는 이 옵션으로 연속 경로를 검사한다.
- `JANGSONI_FLOW_REF`로 과거 커밋 HTML에 같은 검사를 적용할 수 있다. `JANGSONI_FLOW_URL`은 실제 배포 주소 검사에 사용한다.

현대해상에서는 최종 전환 처리 적용 후 `test:regression`도 통과했다. main과 원본 함수 80개·연결 36개·내장 데이터 2종을 대조했으며 입력/편집 항목 106개, 타임라인 6개 시나리오·판례 8개 상태·약관 3개 분류·KCD 검색 4종·분쟁조정 20개 상태·카드뉴스 7개 양식이 일치했다. PNG 저장·편집 저장/초기화·뒤로가기/앞으로가기·7개 직접 진입도 통과했다. 업무 스크립트·데이터·페이지 템플릿·이미지는 이번 수정 전과 파일 차이가 없다.

오리지널의 최종 코드에서는 느린 카드 안 입력·변환 터치의 취소 불가능한 이벤트·넘침·탭·기능 진입을 `test:mobile-devtools`의 세 크기와 `test:mobile-pointer`의 두 크기로 추가 검사했다.

`3a13428`/`ec5e34e`/`d15f0eb`에는 긴 결과 예시를 읽을 때 캐릭터가 다시 모서리로 이동하지 않도록 하는 조건도 들어 있다. 결과 예시 진입 시 한 번만 이동하며, 그 안에서 맨 아래로 내려가는 동작은 이동 횟수를 늘리지 않게 한다. 이는 새로 추가한 ‘읽기 끝’ 목적지의 부수 효과를 막는 수정이다.

세 브랜치의 위 HTML을 각각 별도 미리보기로 열어 390×844·320×568에서 마지막 카드 → 결과 예시 → 입력을 추가 검사했다. 여섯 경우 모두 캐릭터 이동이 한 번이고 입력 화면에 도착했다. 첫 두 브랜치에서 이 조건을 추가하기 전 실행한 연속 경로 검사와, 조건 추가 후의 이동 횟수 검사를 구분한다.

### 검사 중 일시 실패 기록

병렬 실행 중 가이드 320px의 소개 역방향 경계 건너뜀, 가이드의 보행 프레임 샘플 수, 현대해상의 깜빡임 반복 시간 상한 검사가 각각 한 번 실패했다. 당시 경계 건너뜀 메시지에는 좌표가 없어 진단 정보를 추가했다. 같은 가이드 HTML의 전체 6개 입력/크기 조합, 보행의 세 크기, 현대해상의 깜빡임을 단독 재검사했을 때는 통과했다. 깜빡임 코드나 보행 이미지는 수정하지 않았고 프레임 수·시간 기준을 완화하지 않았다. 이 일시 실패들의 별도 원인은 확정하지 않았다.
